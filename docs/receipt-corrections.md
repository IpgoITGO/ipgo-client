# 입고 확인 UI 계약과 검증

연결: [Client #243 / IPGO-160](https://github.com/IpgoITGO/ipgo-client/issues/243),
[Server #134](https://github.com/IpgoITGO/ipgo-server/issues/134).
기존 Server TD31의 receipt-corrections 계약을 사용하며 Server·AI 변경은 없습니다.

## 사용자 흐름

- 메뉴에서 현재 미해결 건수(20건을 넘으면 하한 표시)와 목록/완료 이력을 조회합니다.
- 목록은 서버 cursor로 다음 항목을 명시적으로 읽습니다. 계정이 바뀌면 캐시를 분리합니다.
- 상세에서 이전/최신 원본·누락/검산·수량·기존 배정·현재 발주를 비교합니다.
- KEEP은 기존 처리 유지, REPLACE는 선택한 발주 전량의 새 목록, 빈 목록은 별도 “전체 해제” 선택입니다.
- 서버 capabilities와 sourceReady가 허용하지 않으면 쓰기를 막습니다. 자동 선택/부분 배정은 없습니다.
- 이유(최대500자)와 동작을 정하고 preview를 받아 전후 배정·해제 발주·예정 물량/계산 영향을 봅니다.
- 확인 checkbox 후 decisions를 보냅니다. 저장 성공과 후속 run의 완료/실패를 구분합니다.

## 요청과 복구

GET 목록/상세, POST preview/decisions를 사용합니다. preview는 서버에서 행 잠금을 잡아
현행 자료로 검토하므로 단순 캐시 계산으로 대체하지 않습니다. 실제 개발 환경 호출은 별도 승인 대상입니다.

expectedVersion·동작·정렬된 receiptIds·reason·idempotencyKey를 미리보기 시점에 고정합니다.
미리보기 뒤 내용을 바꾸면 새 검토와 새 키가 필요합니다. 저장 요청 시작 전에 같은 계정/항목의
요청과 미리보기를 sessionStorage에 보관합니다. 인증 토큰은 이 보관 내용에 넣지 않습니다.
응답 유실 뒤 페이지를 다시 열어도 같은 요청/키만 수동 재확인하며 자동 POST 재시도는 없습니다.
기존 인증 클라이언트의 401 갱신 재전달에도 같은 JSON 본문이 유지됩니다.

- ready: 변경 영향을 확인한 뒤 저장하거나 다시 검토할 수 있습니다.
- unknown: 응답을 확정하지 못한 상태입니다. 내용을 바꾸지 않고 같은 저장 요청의 결과만 확인합니다.
- 409 stale/unavailable: 최신 자료를 읽고 새 검토를 요구합니다. 자동 재전송하지 않습니다.
- 키 충돌: 기존 요청을 새 키로 우회하지 않습니다.
- 400/401/403: 입력/인증/권한 안내를 구분하고 성공으로 표시하지 않습니다.
- 최신 정제 PROCESSING/FAILED: 이전 자료와 배정을 보존하고 재조회만 제공합니다.

성공 또는 로그아웃 때 해당 임시 상태를 정리합니다. 실제 업무 원장·DB·S3 자료 삭제가 아닙니다.
탭을 완전히 닫으면 미확인 요청의 임시 보관은 사라집니다. 이후 최신 상태/확인 이력을 먼저 읽어야 하며
브라우저 보관만으로 저장 성공을 추정하지 않습니다.

## 과거 업로드와 최신 상태

U2의 receiptMatching은 업로드 당시의 snapshot입니다. 모든 현행 reason과 미지 reason을 안전한
문구로 보여 주고 현재 목록/상품·발주 조회로 연결합니다. 정제 DONE과 입고 확인 완료는 다릅니다.
정정 성공 뒤 과거 보고서의 경고를 프런트에서 지우거나 현재 상태로 덮어쓰지 않습니다.
현재 목록/상세·발주·SKU·대시보드·업로드 조회는 필요한 범위에서 무효화해 서버를 다시 읽습니다.

## 검증 범위

Vitest/MSW 계약 회귀는 조회 무변경,160→200/120/0·누락/검산 불가, capabilities,
KEEP/REPLACE/전체 해제, preview/최종 확인, 가용량 거부,409 stale,응답 유실/재마운트/키 재사용,
중복 클릭,401/403/서버 오류,늦은 정제/실패,후속 계산 실패,과거 snapshot 보존,
초점 복귀·cursor 조회를 검증합니다. 모델의 임시 저장은 계정/항목 분리와 로그아웃 정리를 검사합니다.

실제 개발 브라우저/DB 쓰기·LLM 비용 검증은 dev 배포 승인 뒤 별도 범위입니다. MSW와 로컬 응답
주입 검증을 실제 서버 시험으로 합산하지 않습니다. 기본 MSW에는 확정 가능한 가짜 항목을 자동
생성하지 않으며, 시험 모드 화면에 실제 서버 저장이 아님을 표시합니다.
