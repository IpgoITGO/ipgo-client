# IPGO-112 모의 서버 재연결 검증

## 범위와 원인

- 대상: [IPGO-112](https://ehwiya.atlassian.net/browse/IPGO-112), [Client #142](https://github.com/IpgoITGO/ipgo-client/issues/142)
- 흐름: 로그인 화면 → API 전송 전 워커 준비 → CSRF·로그인 요청 → 모의 인증 응답 → 오류 안내
- MSW 워커가 재시작되면 메모리의 활성 클라이언트 목록이 비워진다. 기존 코드는 focus와
  visibilitychange에서만 재등록해, 포커스된 탭에서는 다음 API 요청이 모의 응답을 우회할 수 있었다.
- Chromium에서 탭을 visible로 유지한 채 CDP로 워커를 중단했을 때, 기존 코드는 포커스 이벤트
  0회 상태에서 CSRF 요청이 CONNECTION_FAILED(404)로 실패했다.

## 변경

- 모의 API 부트스트랩에서만 API 준비 검사를 연결한다. 실제 API 모드의 클라이언트는
  MSW 모듈을 import하거나 워커를 등록하지 않는다.
- 각 실제 HTTP 요청 전 현재 제어 워커에 MOCK_ACTIVATE를 보내고, 같은 워커의
  MOCKING_ENABLED 응답을 확인한 뒤 전송한다. 동시에 시작된 요청은 진행 중인 준비를 공유한다.
- 앞선 준비 성공을 다음 요청까지 캐시하지 않는다. 제어 워커가 바뀌거나 전송에 실패하거나
  3초 안에 응답하지 않으면 HTTP 요청을 보내지 않고 기존 연결 오류로 안내한다.
- 복구를 이유로 HTTP 요청을 재전송하지 않는다. 기존 CSRF/JWT 처리와 비밀번호 오류 구분은 유지한다.
- listener·timer와 HMR의 준비 검사·포커스 listener를 정리한다.

## 브라우저 확인 결과

| 조건 | 결과 |
|---|---|
| 워커 중단 후 포커스 이동 없이 API 호출 | 준비 확인 후 성공, 포커스 이벤트 0회 |
| 워커 중단 후 잘못된 로그인 | POST 1회, 기존 비밀번호 오류 문구 표시 |
| 워커 준비 응답 차단 | 약 3.37초 뒤 연결 오류, 로그인 POST 0회 |
| 차단 해제 후 사용자가 다시 시도 | POST 1회, 정상적인 비밀번호 오류 응답 |
| 모의 API를 끈 모드 | 워커 등록 0건, 모의 브라우저 모듈 미로딩, 로그인 POST 1회 |

모의 API를 끈 모드의 HTTP 응답은 브라우저 테스트에서 통제했다. 실제 백엔드와의 로그인
통합 검증은 아니다. Chromium 이외의 브라우저는 이번에 실행하지 않았다. 개발 서버의 HMR은
같은 모듈에 timestamp URL을 붙일 수 있어, API 직접 호출 검증은 앱이 실제 로드한 모듈 URL을 사용했다.
로그인 화면 검증은 실제 폼을 통해 수행했다.

## 유지보수와 복구

- 현재 lockfile의 MSW 3.0.3 메시지 프로토콜에 의존한다. MSW 업그레이드 시 브라우저 시작
  흐름과 강제 워커 중단·시간 초과·중복 전송 방지를 함께 재검증한다.
- 생성된 public/mockServiceWorker.js는 수정하지 않았다. 고정 간격의 HTTP ping이나 POST 자동
  재시도를 추가하지 않았다.
- 코드 복구 기준은 변경 전 dev b6e43bd다. 코드 rollback은 새 복구를 제거하며 기존의
  포커스 이벤트에 의존하는 제한이 다시 나타날 수 있다.
