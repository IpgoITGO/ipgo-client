## 1. 한눈에 보는 결론

최종산출물 폴더는 제품 개발 완료본이 아니라 **1차 기획·설계 기준 묶음**이다. 서비스 목표,
계산식, 화면 흐름, 요구사항, API 예시까지 구체화되어 있어 구현의 출발점으로는 충분하다. 다만
다음 이유로 그대로 구현 기준으로 사용하면 안 된다.

1. AI 인사이트의 수치 삽입·대조 책임이 FastAPI와 Spring Boot 사이에서 문서마다 다르다.
2. 직접 입력 시나리오를 새 계산으로 볼지 기존 결과의 하위 시나리오로 볼지 결정이 충돌한다.
3. 10월 23일 API 명세와 현재 Server API가 인증·업로드 계약부터 다르다.
4. 요구사항 74건 중 상태가 기록된 것은 3건뿐이라 전체 진척도를 설명하지 못한다.
5. 발표자료의 요구사항·API·테이블 개수가 원본 문서와 맞지 않는다.
6. Client·Server·AI 구현은 진행 중이지만 통합 E2E와 최종 검증 결과는 아직 증빙되지 않았다.

따라서 현재 우선순위는 기능을 더 추가하는 것이 아니라 **계약 확정 → 요구사항 추적 → 통합 검증**
순서로 기준을 정리하는 것이다.

## 3. 제품 기준선

### 3.1 해결하려는 문제

풀필먼트를 사용하는 소규모 온라인 셀러는 창고별 수불부를 수기로 대조하고 경험으로 입고량을
정한다. 적게 입고하면 품절과 판매 중단이 생기고, 많이 입고하면 보관료와 유통기한 임박 재고가
늘어난다. 서비스는 하나의 정답을 강요하지 않고 권장 수량과 대안별 결과를 함께 보여줘 셀러가
근거를 이해하고 결정하도록 돕는다.

### 3.2 핵심 사용자 흐름

```mermaid
flowchart LR
    A[회원가입·로그인] --> B[수불부 XLSX 업로드]
    B --> C[정제·재고 검산]
    C --> D[입고 조건·기존 발주 확인]
    D --> E[출고 예측·권장량 계산]
    E --> F[80·100·120%·직접 입력 비교]
    F --> G[AI 인사이트]
    G --> H[셀러가 서비스 밖에서 입고 결정]
```

### 3.3 역할 경계

| 주체              | 책임                                                        | 하지 않는 일                  |
| ----------------- | ----------------------------------------------------------- | ----------------------------- |
| 셀러              | 수불부 업로드, 조건 입력, 시나리오 확인, 최종 입고 결정     | 계산 정책 임의 변경           |
| Client            | 인증 화면, 업로드, 상태 조회, 대시보드, SKU 상세, 입력 검증 | 권장량·위험 계산              |
| Spring Boot       | 인증·권한, 파일·입력·결과·이력 저장, FastAPI 호출, 조회 API | LLM으로 수량 결정             |
| FastAPI 계산 엔진 | 정제·검산, 예측, 권장량, 시나리오, 위험, 백테스트           | DB 쓰기, 최종 발주            |
| AI 인사이트       | 엔진 결과를 설명하는 문장 생성·검사·대체                    | 수량·위험·계산 방식 변경      |
| 외부 LLM          | 허용된 구조 안의 문장 초안 작성                             | 원본 수불부·원가·계정·DB 접근 |

AI가 계산값을 만들지 않고, 계산 불가를 0개로 바꾸지 않으며, 최종 결정과 발주는 셀러가 한다는
경계는 모든 산출물에서 일관된다.

### 3.4 계산 기준 요약

| 항목            | 기준                                                                           |
| --------------- | ------------------------------------------------------------------------------ |
| 기준일 `t`      | 업로드한 수불부의 마지막 날짜                                                  |
| 계산 시작일 `s` | 오늘. `s-t`가 7일을 넘으면 계산하지 않고 재업로드 안내                         |
| 커버 기간 `H`   | 입고 주기 + 리드타임                                                           |
| 계산식 A        | 작년 동일 구간 출고에 올해 직전 구간 추세를 반영                               |
| 기준 B          | 최근 최대 28일의 유효 관측일 평균 출고                                         |
| 기본 방식       | 조정 구간에서 A의 WAPE가 B의 90% 이하이면 A, 아니면 B                          |
| 대체            | 기본 방식을 쓸 수 없을 때 다른 방식 사용, 둘 다 불가하면 사유와 함께 계산 불가 |
| 권장량          | 예상 출고×배수−시작 재고−기존 발주−도착 전 미충족 수요, 입고 단위로 올림       |
| 시나리오        | 권장량의 80%·100%·120%와 직접 입력 수량                                        |
| 위험            | 과거 예측 오차를 적용한 추정치. 도착 전 공통 위험과 도착 후 시나리오 위험 분리 |

유효 관측일, 추세 상·하한, 최소 표본, 위험 추정 방법과 같은 세부 정책은 백테스트 근거와 버전을
남겨야 한다. 발표 예시 수치는 구현 상수가 아니다.

### 4.3 MVP와 제외 범위

Must의 제품 범위는 인증, XLSX 업로드·검증, 정제, 예측, 권장량, 시나리오, AI 인사이트,
입고 필요 목록, SKU 상세, 정확도 검증이다. 아래 기능은 Must 완료 전에 끌어오지 않는다.

- Should: 보관 비용, 유통기한 관리, 자연어 시나리오 질의, 검색·이력, 반응형 화면, 다형식 수불부
- Could·확장: 주간 리포트, 상품군 행동 계획, 다창고 배분, 풀필먼트·발주 연동, 알림 발송
- 명시적 제외: 자동 발주, LLM의 수량 계산, 서비스가 셀러 대신 최종 수량 결정

## 5. 시스템과 데이터 설계

### 5.1 구성

| 영역      | 현재 선택                                        |
| --------- | ------------------------------------------------ |
| Client    | React + TypeScript + Vite                        |
| API·저장  | Spring Boot + PostgreSQL                         |
| 계산·AI   | FastAPI + Python                                 |
| 원본 파일 | DB 밖 파일 저장소                                |
| LLM       | OpenAI API, 구체 모델·보관 정책은 별도 확정 필요 |

DB 쓰기는 Spring Boot만 수행하고 FastAPI는 입력 또는 읽기 전용 데이터로 계산한 뒤 결과를 반환한다.
LLM에는 해당 SKU를 설명하는 최소 구조만 보내고 원본 수불부·원가·계정 정보·다른 SKU는 보내지
않는 것이 기준이다.

### 5.2 데이터 구조

스키마 문서는 Must 기준 16개 테이블을 정의한다.

| 묶음      | 주요 테이블                                                                                                              |
| --------- | ------------------------------------------------------------------------------------------------------------------------ |
| 계정·기준 | `users`, `email_verifications`, `warehouses`, `products`                                                                 |
| 수불부    | `upload_files`, `inventory_units`, `daily_stock_records`, `product_daily_stocks`                                         |
| 입력      | `replenishment_settings`, `planned_receipts`                                                                             |
| 계산·이력 | `calculation_runs`, `run_source_files`, `calculation_results`, `scenario_results`, `backtest_metrics`, `ai_explanations` |

계산 실행·결과·시나리오·인사이트를 ID와 버전으로 묶고 입력 스냅샷을 보관해 같은 입력을 재현하는
구조다. 이 원칙은 직접 입력 시나리오의 ID 정책을 확정해야 실제로 지킬 수 있다.

## 10. 권장 문서 정본 순서

다음 순서는 팀 합의 전 제안이다. 합의되면 각 저장소 README와 작업 규칙에 반영한다.

1. 실제 API·schema 정본: Server OpenAPI, AI `schemas/`, Client request schema
2. 결정 근거: 날짜와 상태가 있는 ADR·결정 기록
3. 요구사항과 완료 조건: 요구사항 ID와 연결된 Jira·GitHub Issue
4. 현재 운영·실행 방법: 저장소 README와 운영 문서
5. 과거 기획·발표자료: 배경과 의도 참고용, 현재 계약으로 사용하지 않음

문서가 충돌하면 코드가 무조건 옳다고 보지 않는다. 최신 요구사항과 다르면 Issue를 만들고 결정한
뒤 코드와 문서를 같은 PR에서 함께 수정한다.
